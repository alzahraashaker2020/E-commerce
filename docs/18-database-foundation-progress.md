# أساس إدارة قواعد المتاجر — الدفعة الأولى

## المنفذ

أصبح مسار SQLite الحالي يستخدم سجل `__ShopSchemaVersions` بإصدارات متسلسلة، بدل إعادة فحص وتنفيذ كل ترقيات البيانات في كل تشغيل. الإصدارات الحالية:

1. علامة خصم المخزون ومعرض صور المتغير.
2. العملات وحالات الطلب وربط الطلبات القديمة بها.
3. المحافظات والمناطق ومرجع منطقة الطلب.
4. فهارس مراجع الحالة والمنطقة.

كل دفعة ترقية تُنفذ داخل معاملة واحدة، مع إعادة قراءة الإصدار بعد الحصول على قفل SQLite. إذا فشل التحقق، تُلغى تغييرات المخطط والبيانات وسجل الإصدارات معًا. لا تُحذف القاعدة ولا تُعاد تعبئتها كحل لفشل الترقية.

قبل ترقية قاعدة ملفية موجودة، تُؤخذ نسخة متسقة باستخدام SQLite Backup API في مجلد `backups` بجوار قاعدة البيانات. فشل النسخ الاحتياطي يمنع بدء الترقية. قاعدة جديدة أو قاعدة بالإصدار الحالي لا تنشئ نسخة احتياطية في كل تشغيل. تشغيل عمليتين متزامنتين قد ينتج نسختين احتياطيتين، لكنه لا يكرر إصدارات الترقية.

يُفحص وجود أعمدة النموذج ومراجع المفاتيح الخارجية، ويُرفض المخطط الأحدث من التطبيق أو سجل الإصدارات المتقطع أو مخطط كتالوج أقدم غير مدعوم. هذا تحقق من الأعمدة وسلامة المراجع، وليس مقارنة كاملة لكل قيد أو نوع أو فهرس في قاعدة البيانات.

## التحقق

- بناء API ناجح؛ تحذيرات الحزم والإطار السابقة باقية.
- 24 تحققًا مباشرًا من قاعدة البيانات، تشمل إنشاء قاعدة، عدم تكرار الترقية، الاحتفاظ بالبيانات والإعدادات، قراءة نسخة احتياطية واستعادتها ثم ترقيتها، إضافة الأعمدة الناقصة، التراجع عند الفشل، رفض مخطط أحدث، رفض تاريخ متقطع، وبدء عمليتين معًا.
- إعادة 337 فحص HTTP/قيمة متوقعة للتجارة والصور والشحن والصلاحيات على نسخة قديمة مؤقتة بعد ترقيتها: ناجحة.
- حُدّث API المحلي بعد نجاح الاختبارات. أُنشئت نسخة احتياطية قبل اعتماد سجل الإصدارات، وظل عدد المنتجات 15 قبل وبعد. لم تُنشأ متاجر أو حسابات تجار جديدة.

لتشغيل فحوصات المخطط:

```powershell
dotnet run --project tests/Shop.SchemaChecks/Shop.SchemaChecks.csproj
```

لتشغيل اختبارات المتجر بعد بناء API:

```powershell
pwsh -File tests/security-smoke.ps1 -AdditionalChecks tests/product-order-checks.ps1
```

## ضوابط التطوير التالية

- لا تُغيّر دلالة إصدار ترقية سبق اعتماده؛ تُضاف نسخة جديدة وتُختبر على نسخة من الإصدار السابق.
- النسخ الاحتياطية تحتوي بيانات المتجر؛ لا تُنشر تحت wwwroot ولا تضاف إلى Git. امتداد `.db` مستبعد بالفعل من Git.
- الاستعادة تُجرب على مسار منفصل أولًا؛ لا يستبدل التطبيق قاعدة حية تلقائيًا بنسخة احتياطية.
- عند تعدد المتاجر، التهيئة والترقية مسؤولية إجراء إدارة مخصص يعرف المتجر وقاعدته، لا أثرًا جانبيًا لأول طلب زائر للمتجر.

## ما لم يكتمل بعد

مرحلة T1 لم تكتمل بالكامل من ناحية التشغيل: ما زال مطلوبًا إدارة أسرار ونسخ احتياطي واستعادة خاصة ببيئة الإنتاج. اكتمل اختبار سلسلة مخطط PostgreSQL الموضحة أدناه؛ لا يعني ذلك نشر قواعد إنتاج أو تشغيل عدة تجار.

لا يوجد حتى الآن سجل منصة أو حساب تاجر أو اختيار قاعدة حسب المتجر أو فصل توكنات وملفات بين التجار. ذلك ضمن T2 بعد استكمال أساس المخطط المستهدف. مصدر التطبيق الجاري لا يزال يخدم متجرًا واحدًا.

## تسوية PostgreSQL — 26 أكتوبر 2026

- أضيفت ترقية بين المخطط الأصلي وترقيات المخزون والصور والإعدادات والشحن. تحتفظ بالمنتجات والمتغيرات القديمة، بما فيها المتغير 1012، وتنسخ المخزون وحدود التنبيه إلى حقول النموذج الحالي.
- تتحول خيارات المقاس واللون المعروفة إلى جداول الأبعاد. تبقى الخيارات الأصلية محفوظة؛ الخيارات الأخرى مثل Pattern تحتاج مراجعة لاحقة ولا تُصنف تلقائيًا كمقاس أو لون. جدول المخزون الأصلي محفوظ باسم LegacyInventoryItems للأرشفة، وليس مصدر الرصيد الحالي.
- قاعدة قديمة بلا إعداد عملة تحتفظ بوحدة USD الأصلية؛ لا تحدث إعادة تسعير أو تحويل. العناوين القديمة غير المسجلة تبقى فارغة، وحالة الدفع المضافة Pending؛ لا تعتبر الترقية الطلبات القديمة مدفوعة أو تخصم مخزونها بأثر رجعي.
- الترقية الجديدة للأمام فقط؛ استعادة نسخة احتياطية مجربة هي مسار الرجوع. تُرفض الأرصدة السالبة قبل اعتماد التحويل، وتُرجع المعاملة تغييرات المخطط والبيانات عند الفشل.
- أُصلحت أنواع بيانات إدراج الحالات، ونهايات أوامر SQL، وضبط تسلسل معرفات الحالات لتعمل السكربتات القابلة للتكرار. حُدث snapshot للمخطط الحالي دون حذف بيانات التاجر أو استبدالها بالبذور الحالية.
- نجح 33 تحققًا فعليًا على PostgreSQL 18.6 مؤقت: إنشاء بالترحيلات، إنشاء بسكربت قابل للتكرار، ترقية المخطط الأصلي مع الاحتفاظ بتعديل تاجر، حفظ متغير جديد بمعرض صورتين ورصيد، إضافة حالة جديدة، تنفيذ السكربت مرتين، والتراجع عند مخزون غير صالح. نجحت أيضًا فحوص SQLite الـ24. لم تتغير قاعدة المتجر المحلية في هذه الدفعة.
- استخدم الاختبار [الحزمة الرسمية المحمولة](https://www.postgresql.org/download/windows/) على منفذ محلي عشوائي بمصادقة كلمة مرور، وأُوقفت قواعد الاختبار بعد الانتهاء. لم تُثبت خدمة نظام.

تشغيل الاختبار مع مسار bin لحزمة PostgreSQL محلية، بعد استعادة تبعيات المشروع:

```powershell
pwsh -File tests/postgres-schema-checks.ps1 -PostgresBin src/Shop.Api/obj/postgres-runtime/pgsql/bin
```

السكربت ينشئ مجموعة قواعد مؤقتة تحت obj ويوقفها في finally، ولا يتصل بقاعدة المتجر. الاختبار المباشر `--postgres` يتطلب SHOP_TEST_POSTGRES على 127.0.0.1 ومنفذ غير 5432. التحقق لا يغطي بعد نسخة PostgreSQL منشورة سابقًا بترقيات يدوية خارج سجل EF؛ يلزم فحص ونسخة احتياطية قبل ترقية أي بيئة حقيقية.

تحديث لاحق: بدأ تنفيذ T2 وأُثبت عزل قواعد المتاجر وتوكناتها وصورها. الحالة الحالية وحدود إدارة حسابات التجار في [فصل المنصة والتاجر](19-platform-merchant-isolation.md).
