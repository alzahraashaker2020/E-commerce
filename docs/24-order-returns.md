# Returns, inspection and recorded refunds

Customers request a return from account order history; guests use the tracking page with the private order code. A delivered order with deducted stock is required. Each request targets one original order item and may return part of its purchased quantity. A request key makes retrying safe. Non-rejected requests reserve their quantities, so overlapping requests cannot exceed the purchased amount.

Merchants use `/merchant/returns`: Requested → Approved → Received → Completed. Requested/Approved may be rejected with a note. Inspection requires an explicit choice about restoring sellable stock. Approval alone never changes inventory. Receive restores only the requested quantity to the original product or size/color variant, once, in the same transaction as the return transition and audit event. Damaged goods can be received without restoring inventory. Delivered orders cannot be reopened or cancelled through fulfillment status changes.

The merchant records a manual payment after inspection, with amount, reference and notes. This does not call a payment gateway or transfer money. A positive amount requires a reference; zero requires the decision note. The maximum suggested product refund allocates the original discounted/taxed merchandise value to the returned quantity, rounded down to two decimal places, excluding shipping. This is a product rule, not a legal return policy. Original order totals and payment status are preserved; no captured-payment ledger or automatic provider refund exists yet.

Every transition has a version check, transaction and immutable history event. Customer ownership/private proof and tenant database isolation apply to requests and reads. Merchants can inspect event history. Return status updates use the durable email outbox. Rejected quantities can be requested again. Exchange orders, configurable return periods/policies, shipping refunds, automatic provider refunds and net-sales reporting remain future work.

SQLite startup upgrades additively to version 8 and retain a backup of an existing database. PostgreSQL must apply OrderReturns after DurableEmailOutbox.
