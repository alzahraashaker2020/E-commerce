# صحة الدفع وربط العميل ومنع تكرار الطلب — 26 أكتوبر 2026

## الدفع

الدفع المتاح حاليًا Cash فقط. Card معطل في الواجهة ومرفوض في الخادم قبل حفظ أي طلب، حتى عند إرسال الطلب يدويًا. الطلب النقدي يحفظ CashOnDelivery وليس Paid. ربط مزود دفع وتوقيعات callbacks والتحصيل والاسترداد ما زال لاحقًا. لم تُغيّر حالات دفع الطلبات القديمة بأثر رجعي.

## هوية العميل

Checkout يرسل توكن العميل عند تسجيل الدخول. الخادم يتحقق من التوكن والمتجر ويستمد CustomerId من الهوية الموثقة، مع الاسم والإيميل من حسابه. لا يثق بمعرف عميل أو بريد مكتوب لتحديد مالك الطلب. الطلب يظهر في `/api/account/orders` لصاحبه فقط. Guest checkout يبقى متاحًا، ولا يلحق طلب ضيف بحساب موجود لمجرد تطابق البريد. التوكن غير الصالح يرفض 401 ولا يتحول الطلب إلى ضيف بصمت، وتوكن التاجر لا يمثل حساب عميل.

## إعادة المحاولة

كل طلب إنشاء يحتاج IdempotencyKey من نوع UUID غير فارغ. تنشئ الواجهة مفتاحًا جديدًا لكل محاولة جديدة وتحتفظ بالطلب والمفتاح محليًا حسب المضيف وحساب العميل/الضيف حتى تتأكد النتيجة. عند مشكلة اتصال يمكن الضغط على Retry previous submission، بما في ذلك بعد إعادة تحميل الصفحة، لإرسال نفس الطلب بمفتاحه. لا تغير الواجهة طلبًا غير مؤكد إلى محاولة جديدة تلقائيًا.

CheckoutReceipts داخل قاعدة كل متجر يحفظ المفتاح وصاحب المحاولة وبصمة تفاصيلها ونتيجة التأكيد. الطلب وبنوده والإيصال يحفظون في معاملة واحدة. إعادة نفس المفتاح والتفاصيل ترجع النتيجة الأصلية قبل إعادة التحقق من السعر أو المخزون الحاليين. استخدام المفتاح بتفاصيل أو هوية مختلفة يرفض 409. قيد المفتاح في قاعدة البيانات يمنع طلبين عند الإرسال المتزامن؛ الطلب الخاسر يتراجع بالكامل ويعيد نتيجة الطلب الأول. الأرقام أو المفاتيح في متجر آخر لا تختلط لأن القواعد والتوكنات معزولة.

لا يرسل إيميل التأكيد مرة ثانية عند replay؛ الإرسال الأصلي بعد اعتماد المعاملة فقط، وما زال best effort دون outbox. تغير سعر المنتج لاحقًا لا يغيّر تأكيد طلب محفوظ. محاولة جديدة مقصودة بمفتاح جديد تعني طلبًا جديدًا؛ هذه الحماية تمنع تكرار نفس محاولة الإرسال، وليست منع شراء العميل نفس المنتجات مرة أخرى.

الفشل قبل حفظ الطلب يترك السلة ولا يحفظ إيصال نجاح. يرسل الخادم X-Checkout-Outcome:NotCreated عند رفض تفاصيل/مخزون/سعر الطلب قبل الحفظ؛ تسمح الواجهة بتصحيح المحاولة في تلك الحالة. الفشل غير المؤكد يحتفظ بالطلب والمفتاح. السلة لا تُفرغ عند استعادة طلب قديم إذا كانت تغيرت إلى سلة مختلفة.

## الترحيل والتحقق

- SQLite إلى الإصدار 5 مع نسخة احتياطية قبل الترقية ومعاملة واحدة. تُرقى قواعد SQLite المسجلة الجاهزة عند بدء التطبيق، دون إنشاء بديل تجريبي لقاعدة تاجر مفقودة.
- PostgreSQL: migration `20261026010000_CheckoutReceipts`. يجب تطبيقه صراحةً لكل قاعدة إنتاج قديمة باستخدام ShopContext ومرجع اتصال المتجر، قبل نشر الميزة؛ إنشاء المتاجر الجديدة يطبق السلسلة كاملة. الجدول الداخلي لا يغير نموذج الطلب أو بياناته القديمة.
- نجح بناء API وAngular للإنتاج و24 فحصًا لمخطط SQLite. نجح 379 فحص HTTP للتجارة وصحة Checkout، تشمل ربط العميل وعدم انتحال صاحب بريد، رفض البطاقة، إعادة الطلب بعد تغيير السعر وإعادة تشغيل API، إيميل واحد، وأربع محاولات متزامنة تنشئ طلبًا واحدًا.
- جربت ملكية Checkout والتزامن على PostgreSQL أيضًا ضمن اختبارات المتجرين، مع إنشاء قاعدة جديدة والترقية والسكربت القابل للتكرار.

```powershell
pwsh -File tests/security-smoke.ps1 -AdditionalChecks tests/checkout-integrity-checks.ps1
pwsh -File tests/postgres-schema-checks.ps1 -PostgresBin <postgres-bin-path> -ApiIsolation
```

المفتاح والإيصالات لا تنتهي تلقائيًا حاليًا لضمان أن إعادة محاولة قديمة لا تنشئ طلبًا جديدًا. وضع سياسة احتفاظ/تنظيف أو outbox أو بوابة دفع يأتي بترقية مستقلة.
