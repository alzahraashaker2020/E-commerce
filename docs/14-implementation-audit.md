# مراجعة تنفيذ متطلبات التجارة الإلكترونية

تاريخ المراجعة: 25 أكتوبر 2026.

> هذه لقطة ما قبل الإصلاحات. بدأ تنفيذ SEC-01 وSEC-02 والتحقق منهما لاحقًا؛ راجع [الخطة وسجل الإنجاز](15-product-backlog.md) للحالة الحالية.

المرجع: https://chatgpt.com/share/6ade4a96-889c-83ea-856c-8e0902f4e225

## النتيجة

المشروع لم ينفذ كل المتطلبات الواردة في المحادثة. يوجد أساس للمتجر ولوحة الإدارة، ومقاسات وألوان ومتغيرات للمنتجات، لكن دورة الشراء والشحن والدفع والمخزون غير مكتملة. لا يمكن اعتماد المشروع على أنه اجتاز سيناريوهات القبول أو أنه جاهز للبيع في حالته الحالية.

هذه مراجعة للكود الحالي والبناء. تمت قراءة المتطلبات الظاهرة في صفحة المحادثة، ومنها طلبات المستخدم الخاصة بالتصنيفات والشحن والمخزون والمتغيرات والإيميلات والدفع، وملخص المراحل A–H. لم تُستخرج قائمة اختبارات القبول الـ46 كاملة بندًا بندًا من البرومبت النهائي؛ لذلك لا يدّعي التقرير تغطية كل تفاصيلها أو حساب نسبة إنجاز دقيقة.

## التحقق المنفذ وحدوده

- بناء Angular بالإعداد الافتراضي: ناجح.
- بناء Shop.sln دون استعادة الحزم، مع تعطيل المترجم المشترك: ناجح، صفر أخطاء وثلاثة تحذيرات.
- تحذيرات البناء تشير إلى انتهاء دعم net7.0، وتنبيه أمني لحزمة AutoMapper 12.0.0، وتنبيه لحزمة System.IdentityModel.Tokens.Jwt 7.0.3. هذه رسائل البناء، وليست مراجعة مستقلة لآخر حالة للثغرات.
- بدأ الـAPI على قاعدة SQLite منفصلة داخل مجلد مؤقت؛ لم تُستخدم قاعدة بيانات المشروع للاختبارات.
- تعذر تنفيذ طلبات HTTP التجريبية لأن البيئة منعت الاتصال المحلي بالمنفذ 5187. أُوقفت عملية الاختبار بعد المحاولة. لا توجد نتائج تشغيل تثبت نجاح أو فشل إنشاء الطلب أو الصلاحيات.
- لم أجد مشروع اختبارات Backend أو ملفات اختبارات فعلية للواجهة ضمن مصدر المشروع؛ يوجد إعداد tsconfig.spec.json فقط. لا يوجد دليل محلي على اجتياز اختبارات القبول الـ46.
- لم تتغير ملفات تنفيذ التطبيق. تغييرات package-lock والنسخة الاحتياطية ومجلد uploads كانت موجودة قبل المراجعة.

## مقارنة المتطلبات بالتنفيذ

«موجود في الكود» لا يعني أنه اجتاز اختبارًا أثناء التشغيل.

| المتطلب | الحكم من الكود | الملاحظة |
|---|---|---|
| إنشاء الطلب وإرجاع رقم تأكيد | جزئي، يحتاج تحقق تشغيل | يوجد endpoint وحفظ Order وItems، لكن خطأ Checkout الأصلي لم يُعاد إنتاجه |
| حساب الأسعار والخصم في الخادم | موجود في الكود | السعر يؤخذ من المنتج أو المتغير؛ الشحن غير مدمج |
| تفريغ السلة بعد نجاح الطلب فقط | موجود في الكود | الواجهة تفرغ السلة بعد استلام orderNumber |
| منع تكرار الطلب | جزئي | يوجد submitting في الواجهة؛ لا يوجد مفتاح idempotency أو منع لإعادة الطلب نفسه في الخادم |
| مراجعة المخزون وقت الشراء وخصمه | ناقص | لا توجد مقارنة بالكمية المتاحة أو عملية خصم في Checkout |
| إعادة المخزون عند الإلغاء | ناقص | تغيير الحالة لا ينفذ حركة مخزون |
| محافظات ومناطق قابلة لإدارة الأدمن | غير موجود | لا توجد كيانات أو APIs أو صفحات إدارة لها في المصدر الحالي |
| مصاريف شحن حسب المنطقة | غير موجود | ShippingTotal مضبوط على 0 صراحةً، والعنوان حقول نصية |
| تثبيت رسوم الشحن للطلب القديم | غير مكتمل | يوجد حقل ShippingTotal، لكن لا يوجد نظام تسعير شحن يملؤه |
| حالات طلب ديناميكية | غير موجود | OrderStatus عبارة عن enum، والواجهة تحتوي قائمة ثابتة |
| قواعد انتقال الحالات وسجل التغييرات | غير موجود | يتم تعيين الحالة المطلوبة مباشرة، دون سجل تاريخ أو قواعد انتقال |
| إيميل إنشاء الطلب وتغيير الحالة | جزئي | توجد استدعاءات لخدمة SMTP أو سجل تجريبي؛ الإرسال الحقيقي معطل افتراضيًا |
| إعادة محاولة الإيميلات الفاشلة وسجل تسليم دائم | ناقص | الأخطاء تُسجل ثم تُبتلع؛ لا يوجد outbox أو retry queue أو إدارة للمحاولات |
| دفع Card مؤكد من بوابة دفع أو Sandbox | غير موجود | اختيار Card يضع PaymentStatus=Paid مباشرةً |
| تنسيق Visa وMastercard كخيارات دفع | ناقص | يوجد راديو Cash وراديو Card (Visa)؛ لا توجد بطاقات الدفع المطلوبة |
| إنشاء المقاسات والألوان وإدارتها | موجود في الكود | توجد كيانات وControllers وصفحات إدارة وحماية حذف العناصر المستخدمة |
| عدة مقاسات وألوان لكل منتج | جزئي | يوجد نموذج للمتغيرات مع سعر ومخزون وصورة؛ التحقق من التركيبات والتعديل الآمن يحتاج استكمال |
| اختيار مقاس ولون مترابطين في المتجر | جزئي | المعروض أزرار للتركيبات الموجودة؛ لا يوجد اختيار مستقل متكامل للمقاس واللون |
| إظهار أو إخفاء عدد القطع لكل منتج | موجود في الكود | showStockQuantity محفوظ وتستخدمه صفحة المنتج؛ حماية كمية الشراء ناقصة |
| CRUD للتصنيف والتصنيف الفرعي | جزئي | توجد إدارة هيكلية ومنع حذف التصنيف المستخدم، لكن لا يوجد Active أو DisplayOrder |
| قوائم Category ثم Subcategory | موجودة جزئيًا | قوائم مترابطة موجودة؛ لا يوجد مفهوم تفعيل التصنيفات، والتحقق الخلفي من الهيكل غير كافٍ |
| رفع صورة التصنيف من ملف | جزئي | الرفع والمعاينة والحفظ موجودة؛ مسار العرض في المتجر والتحقق الأمني يحتاجان إصلاحًا |
| رفع صورة المنتج وحفظها | غير مكتمل | المعاينة موجودة، لكن buildPayload لا يرسل imageUrl، وProductUpsertRequest لا يحتوي صورة المنتج |
| صور المتغيرات | جزئي | ImageUrl للمتغير يصل للخادم، لكن صفحة المنتج لا تستخدم صورة المتغير المختار |
| Navbar toggle للموبايل | غير موجود | لا يوجد زر فتح/إغلاق أو حالة للقائمة في AppComponent |
| تحسين خيارات تتبع الطلب | جزئي | يوجد تبديل وإدخال مناسب لكل طريقة؛ لا يوجد تحقق ملكية، ولا تكفي مراجعة الكود لاعتماد الشكل بصريًا |
| تتبع آمن بالإيميل | غير مكتمل | الإيميل وحده يكفي للحصول على بيانات آخر طلب، دون تحقق |
| ربط الطلب بحساب العميل | ناقص | Checkout يثبت CustomerId=null، والواجهة لا ترسل توكن العميل له |
| عملة EGP | موجودة في البيانات الأولية الحالية | StoreSettings يبدأ بـEGP؛ بعض الطلبات الأولية القديمة USD |
| SQL Server | غير منفذ، والقرار غير محسوم | الموجود PostgreSQL وSQLite؛ المحادثة نفسها تعرض اختيارًا يحتاج حسمًا، لذلك ليس من الصحيح اعتباره خطأ تنفيذ مؤكدًا |
| ترحيل قاعدة البيانات الحالية | ناقص | Migration وSnapshot قديمان مقارنةً بنموذج المقاسات والألوان والمخزون الحالي |
| تقارير تسليم واختبارات قبول | غير مثبتة | توجد سجلات مهام قديمة تدعي نجاح فحوصات لأجزاء سابقة، لكنها لا تثبت النسخة الحالية |

## أهم العيوب وأدلتها

### 1. صلاحيات الإدارة لا تشترط Admin — أولوية عاجلة

Controllers الإدارة، ومنها AdminProductsController وAdminOrdersController وUploadsController، تستخدم `[Authorize]` فقط. خدمة التوكن توقع توكن العميل وتوكن الأدمن بالإعدادات نفسها، ولا توجد سياسة عامة في Program.cs تفرض دور Admin لهذه المسارات. وفق الكود، توكن Customer صالح يمكنه اجتياز شرط المصادقة لهذه العمليات. حماية مسار Angular لا تعالج حماية الـAPI.

الأدلة: `src/Shop.Api/Controllers/Admin/AdminProductsController.cs:17`، `src/Shop.Api/Controllers/Admin/AdminOrdersController.cs:18`، `src/Shop.Api/Controllers/Admin/UploadsController.cs:15`، `src/Shop.SL/TokenManager/TokenService.cs`، `src/Shop.Api/Program.cs`.

### 2. تسجيل دفع البطاقة كأنه تم تحصيله — أولوية عاجلة

في CheckoutController يتم تعيين Paid عند اختيار Card، دون جلسة دفع أو نتيجة مؤكدة من مزود الدفع. هذا يخالف شرط المحادثة الذي يمنع إعلان نجاح الدفع قبل التأكيد. وحتى في النسخة التجريبية، لا توجد دورة Sandbox واضحة للنجاح والفشل والإلغاء.

الدليل: `src/Shop.Api/Controllers/CheckoutController.cs:161`.

### 3. المخزون لا يحمي الطلبات — أولوية عاجلة

CheckoutController وCartController يحلان السعر والمنتج والمتغير، لكن لا يتحققان من StockQuantity أو IsActive، ولا يشترطان VariantId لمنتج HasVariants. الحفظ لا يخصم المخزون. AdminOrdersController لا يعيده عند الإلغاء. لذلك إخفاء أو إظهار المخزون منفذ بصريًا، لكن سلامة البيع غير منفذة.

الأدلة: `src/Shop.Api/Controllers/CheckoutController.cs`، `src/Shop.Api/Controllers/CartController.cs`، `src/Shop.Api/Controllers/Admin/AdminOrdersController.cs:98`.

### 4. الشحن غير منفذ — أولوية عالية

لا توجد Governorate أو Area أو ShippingRate في النموذج أو APIs الإدارة أو الواجهة. Checkout يثبت ShippingTotal=0 ويحسب الإجمالي من المنتجات والخصم فقط. الحقل وحده لا يحقق المتطلب.

الدليل: `src/Shop.Api/Controllers/CheckoutController.cs:156`، `src/Shop.DAL/Data/ShopContext.cs`، `client/src/app/features/checkout/checkout.component.html`.

### 5. دورة الحالات غير ديناميكية — أولوية عالية

إضافة قيمة إلى enum لا تجعل الحالات قابلة لإنشاء الأدمن. لا توجد إدارة حالة أو انتقالات أو تاريخ حالة. تغيير الحالة يرسل إيميل حتى لو كانت نفس القيمة، ولا يمنع مثلًا الانتقال من Delivered إلى Pending.

الأدلة: `src/Shop.DAL/Models/OrderStatus.cs`، `src/Shop.Api/Controllers/Admin/AdminOrdersController.cs:98`، `client/src/app/features/admin/admin-orders/admin-orders.component.ts`.

### 6. صورة المنتج لا تُحفظ من نموذج الإدارة — أولوية عالية

onProductImage يضع المسار في form.imageUrl، لكن buildPayload لا يتضمنه، وProductUpsertRequest لا يحتوي حقلًا أو مجموعة لتحديث صور المنتج، وAutoMapper يتجاهل Images. وبالتالي نجاح الرفع والمعاينة لا يحقق ربط الصورة بالمنتج، وينطبق الأمر على إزالة الصورة من النموذج أيضًا.

الأدلة: `client/src/app/features/admin/admin-products/admin-products.component.ts:177` و`:235`، `src/Shop.DAL/ViewModels/AdminProductViewModels.cs`، `src/Shop.Api/Mapping/MappingProfile.cs`.

### 7. مسارات الصور لا تتوحد بين الإدارة والمتجر — أولوية عالية

الرفع يعيد `/uploads/...`. الإدارة تضيف أصل الـAPI في previewUrl، بينما صفحات catalog/category/product-detail تربط src بالمسار الخام. عند تشغيل Angular على 4200 والـAPI على 5000 كما في README، يطلب المتصفح الصورة من خادم الواجهة. لا يوجد إعداد proxy في ملفات المشروع الظاهرة يعالج ذلك. قد يختلف السلوك عند النشر على أصل واحد.

الأدلة: `src/Shop.Api/Controllers/Admin/UploadsController.cs`، `client/src/app/features/admin/admin-products/admin-products.component.ts:154`، قوالب catalog/category/product-detail.

### 8. تعديل المتغيرات قد يفشل بعد بيعها — أولوية عالية

تعديل المنتج يمسح المتغيرات ويعيد إنشاءها بدل الحفاظ على معرفاتها. OrderItem وCartItem يربطان VariantId مع DeleteBehavior.Restrict. إذا كان متغير مستخدمًا في طلب، فإن محاولة حذفه أثناء تعديل المنتج يُتوقع أن تُرفض بقيود قاعدة البيانات. وحتى دون مبيعات، تغيير المعرفات يكسر مراجع المتغيرات في سلال العملاء المحفوظة.

هذا استنتاج مدعوم بالكود والقيود؛ لم يُختبر أثناء التشغيل.

الأدلة: `src/Shop.Api/Controllers/Admin/AdminProductsController.cs:125`، `src/Shop.DAL/Data/ShopContext.cs`.

### 9. رفع الملفات يعتمد على Content-Type المرسل من العميل — أولوية عالية

يُقبل أي Content-Type يبدأ بـimage/، ويُحتفظ بامتداد اسم الملف، دون قائمة امتدادات محددة أو فحص محتوى الصورة. لا يكفي ذلك لإثبات أن المحتوى صورة آمنة. يلزم فحص فعلي وقصر الصيغ المقبولة والتعامل الواضح مع SVG والمحتوى النشط.

الأدلة: `src/Shop.Api/Controllers/Admin/UploadsController.cs:53` و`:63`.

### 10. تتبع بالإيميل دون تحقق — أولوية عالية

TrackByEmail endpoint عام، ويعيد رقم الطلب وحالته والمنتجات والكميات والأسعار والإجمالي بمجرد معرفة الإيميل. لا يعيد عنوان التوصيل في النموذج الحالي، لكنه ما زال يكشف معلومات الشراء دون إثبات ملكية الإيميل، خلافًا للمتطلب.

الدليل: `src/Shop.Api/Controllers/OrderTrackingController.cs:54`، `src/Shop.DAL/ViewModels/TrackingViewModels.cs`.

### 11. دخول اجتماعي تجريبي يصدر توكن فعليًا — أولوية عالية

SocialLogin يقسم النص externalId:email:name، ويبحث عن حساب بالإيميل ويصدر له توكن دون التحقق من مزود الهوية. المسار ليس مقيدًا بوضع Demo صريح. توثيق أنه تجريبي لا يمنع استخدامه لانتحال حساب. يتفاقم الأثر مع نقص اشتراط Admin في APIs الإدارة.

الأدلة: `src/Shop.Api/Controllers/CustomerAuthController.cs:106` و`:119` و`:179`.

### 12. الطلبات الجديدة لا تظهر في حساب صاحبها — أولوية عالية

إنشاء الطلب يضع CustomerId=null دائمًا. صفحة حساب العميل تسترجع الطلبات بواسطة CustomerId، وبالتالي الطلب الجديد لا يُربط بالمستخدم المسجل. الإيميل وحده لا ينفذ هذا الربط.

الأدلة: `src/Shop.Api/Controllers/CheckoutController.cs:149`، `src/Shop.Api/Controllers/AccountController.cs`، `client/src/app/core/interceptors/auth.interceptor.ts`.

### 13. ترحيلات قاعدة البيانات قديمة — أولوية عالية

الـSnapshot يحتوي نموذج المتغيرات القديم OptionName، ولا يتضمن نموذج Sizes/Colors/StockQuantity الحالي. إنشاء SQLite جديدة بـEnsureCreated يمكنه العمل، لكنه لا يرقي SQLite موجودة، كما أن migration الحالية لا تمثل النموذج المطلوب لـPostgreSQL. يلزم إعداد ترحيل واختباره على نسخة بيانات منفصلة، دون حذف قاعدة المستخدم.

الأدلة: `src/Shop.DAL/Migrations/ShopContextModelSnapshot.cs:1238`، `src/Shop.DAL/Data/ShopContext.cs`، `src/Shop.Api/Program.cs`.

### 14. إعداد بناء الواجهة للإنتاج يحتاج تصحيحًا — أولوية متوسطة

توجد environment.prod.ts بقيمة /api، لكن angular.json لا يحتوي fileReplacements، والملفات تستورد environment.ts. لذلك نجاح build بإعداد production لا يثبت استخدام عنوان الـAPI الخاص بالإنتاج.

الأدلة: `client/angular.json`، `client/src/environments/environment.ts`، `client/src/environments/environment.prod.ts`.

## ترتيب الإصلاح المقترح

1. إغلاق ثغرات الصلاحيات والدخول الاجتماعي، وتصحيح إعلان حالة الدفع.
2. إثبات Checkout كامل على قاعدة اختبار: مخزون، منتجات ومتغيرات فعالة، خصم ذري، منع تكرار، وربط حساب العميل.
3. إصلاح صور المنتجات وتعديل المتغيرات دون تغيير معرفات العناصر المستخدمة، ثم تحديث واختبار migrations.
4. تنفيذ المحافظات والمناطق وتسعير الشحن وتثبيت التكلفة في الطلب.
5. تنفيذ حالات ديناميكية وانتقالات وسجل تاريخ، وربط آثار المخزون والإيميلات بكل انتقال صحيح.
6. استكمال الإيميلات مع سجل محاولات وإعادة إرسال، ودورة دفع Sandbox قابلة للتحقق.
7. استكمال Navbar وبطاقات الدفع واختيار المقاس واللون والتتبع الآمن، ثم اختبار بصري للموبايل والكمبيوتر.
8. استخراج قائمة القبول النهائية كاملة وتحويلها إلى نتائج PASS/FAIL بأدلة، تشمل حالات الفشل والتزامن، قبل إعلان اكتمال المشروع.

لا توجد نسبة إنجاز موثوقة من هذه المراجعة؛ حجم الأجزاء المتبقية وتأثيرها أهم من عدد الصفحات أو الملفات الموجودة.
