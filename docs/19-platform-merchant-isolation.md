# تفعيل المتاجر وفصل صلاحيات التاجر والمنصة

تم التنفيذ في 26 أكتوبر 2026. التطبيق يختار قاعدة متجر مستقلة لكل طلب حسب hostname مسجل في قاعدة المنصة. لا يعود إلى متجر افتراضي إذا كان المضيف غير معروف. نفس المصدر يخدم جميع المتاجر.

## الصلاحيات والمسارات

| الدور | صلاحياته | الواجهة | API |
|---|---|---|---|
| Merchant | منتجاته وتصنيفاته ومقاساته وألوانه وصوره ومخزونه وطلباته وخصوماته وعملاؤه وعملاته وحالاته وشحنه وإعداداته | `/merchant/*` | `/api/merchant/*` |
| PlatformAdmin | قائمة المتاجر، إنشاء متجر ومالك أول، تفعيل/تعليق متجر | `/platform` | `/api/platform/*` |
| Customer | حسابه وطلباته ومراجعاته في متجره | `/account/*` | `/api/account/*` |

مدير المنصة لا يحصل تلقائيًا على توكن تاجر أو حق قراءة منتجاته وعملائه. التاجر والعميل لا يستطيعان استخدام APIs المنصة. الحساب القديم باسم admin في المتجر الحالي يظل بنفس بيانات الدخول، لكنه يصدر دور Merchant محددًا بمتجره. لا تتحول الحسابات القديمة إلى PlatformAdmin.

تسجيل الدخول: `/api/merchant/auth/login` للتاجر، `/api/platform/auth/login` للمنصة، و`/api/account/login` للعميل. نقلت أسماء controllers وواجهات Angular والخدمات والحارس ومجلدات العرض من Admin إلى Merchant. احتفظت طبقة تخزين المتجر بالكيان/الجدول التاريخي AdminUser/AdminUsers واسم الدور القديم Admin للتوافق مع البيانات؛ لا يمثل أي منها مدير المنصة. حسابات المنصة مستقلة في PlatformContext.

الروابط القديمة `/admin` و`/admin/:page` تحول إلى `/merchant` ونفس الصفحة. APIs القديمة `/api/admin/*` و`/api/auth/login` أزيلت؛ لا يوجد مسار ثانٍ بصلاحية أوسع. حدّث أي عميل خارجي لتلك المسارات. الجلسات القديمة بلا store_id لا تعمل، ويلزم تسجيل الدخول مرة أخرى.

## التسجيل وحل المتجر

قاعدة `shop_platform.db` مستقلة وتحتوي Stores وOperators. يمكن تحديد مسارها بـ `ConnectionStrings:PlatformConnection`. يضاف المتجر الحالي مرة واحدة بمعرف default ومرجع DefaultStore، دون نقل أو حذف بياناته. `Platform:DefaultStoreHost` يحدد مضيفه، والافتراضي localhost. المضيف بدون بروتوكول أو منفذ. Proxy الإنتاج يجب أن يحفظ Host الصحيح؛ لا يثق التطبيق في X-Forwarded-Host عشوائي.

لإضافة متجر، جهّز مرجع اتصال على الخادم أولًا، مثل متغيرات البيئة:

```powershell
$env:StoreConnections__MerchantB__Provider = 'Postgres'
$env:StoreConnections__MerchantB__ConnectionString = '<connection string from protected server configuration>'
```

ثم من `/platform` أدخل الاسم والمضيف ومرجع MerchantB وحساب المالك الأول. لا تدخل سلسلة الاتصال أو كلمة مرور قاعدة البيانات في الواجهة، ولا يعيدها API. يشترط أن تكون القاعدة جديدة/فارغة، ويرفض مشاركة مرجع أو هوية قاعدة مع متجر مسجل. تتم التهيئة بإجراء منصة صريح، وليس أثناء أول زيارة عميل. تحفظ حالة Provisioning ثم Active؛ عند الفشل تبقى Failed وغير متاحة، ولا يمكن تحويلها إلى Active من زر التفعيل. معالجة فشل التهيئة وإعادة المحاولة الإدارية ما زالت تحتاج إجراء تشغيل مخصص؛ لا تحذف قاعدة فاشلة تلقائيًا.

المتاجر الجديدة تبدأ دون منتجات أو عملاء أو طلبات أو حساب admin التجريبي. يضاف المالك بكلمة المرور المختارة وRole Merchant. المقاسات والألوان فارغة؛ العملات والحالات والإعدادات الأساسية متاحة. في هذه النسخة الأولى حساب المالك داخل قاعدة متجره؛ هوية تاجر مركزية مع عضويات متعددة وموظفين بصلاحيات تفصيلية لم تنفذ بعد.

للتجربة المحلية، يوجد مرجع `LocalMerchant2` في appsettings.Development.json لقاعدة shop_merchant2.db. استخدم مثلًا `shop-b.localhost` كمضيف، ثم افتح `http://shop-b.localhost:4200/merchant/login`. المتصفح المحلي يحل نطاقات localhost، وقد تحتاج إعداد DNS/hosts على بيئة لا تدعمها. الفرونت يوجه API إلى نفس hostname على منفذ 5000 في التطوير، وإلى `/api` في بناء الإنتاج. لا تغير رابط API العام لكل تاجر يدويًا.

عند إضافة أول مدير منصة، تضبط `Platform:BootstrapUsername` و`Platform:BootstrapPassword` من بيئة التشغيل، وكلمة المرور 12 حرفًا على الأقل. التهيئة تعمل فقط إذا لم يوجد مدير منصة؛ لا تعيد ضبط حساب موجود عند إعادة التشغيل. لا توجد كلمة مرور منصة افتراضية في المصدر. للنسخة المحلية الجارية أنشئ حساب منفصل، وبياناته محفوظة في `src/Shop.Api/obj/platform-access.json` المستبعد من Git.

## حدود العزل

- ShopContext ونطاق المتجر Scoped لكل طلب. توكنات التاجر والعميل تحمل store_id وتفشل عند اختلاف المضيف. يتأكد التاجر في كل طلب محمي أن حسابه ما زال نشطًا وله دور متجر. مدير المنصة يتحقق من وجود حسابه المركزي.
- ملفات الرفع الجديدة تحت `/uploads/stores/{storeId}/...`، ولا يخدم المضيف صور رفع متجر آخر. روابط الرفع القديمة تبقى متاحة للمتجر الأصلي فقط. صور المنتج العامة تبقى محتوى عامًا داخل متجرها، وليست ملفات خاصة تتطلب تسجيل الدخول.
- سلة العميل وجلساته وجلسة التاجر تشمل المضيف في مفاتيح التخزين، والمضيف المختلف أصل مختلف في المتصفح. جلسة المنصة منفصلة. كاش الإعدادات مرتبط بعمر تطبيق المتجر الذي لا يغير المضيف دون تحميل صفحة جديدة.
- إخراج البريد المحلي تحت store-data/{storeId}/sent-emails. SMTP المتجر الأصلي يستخدم Email، والمتاجر الجديدة StoreEmail:{storeId}، ولا ترث إعدادات الأصل. الدفع الاجتماعي/بوابات الدفع والمهام الخلفية متعددة المتاجر لم تنفذ بعد.
- تعليق متجر يرفض جميع طلباته، ويحتفظ بقاعدته وملفاته. المتاجر الأخرى تعمل. تعريف سياسة معالجة callbacks وطلبات الشحن القائمة عند تعليق اشتراك مؤجل حتى تنفيذ تلك التكاملات.
- الإنتاج ما زال يحتاج أسرار JWT مستقلة وإعداد CORS:Origins محددًا، ومستخدم PostgreSQL بصلاحيات قاعدة متجره، ونسخًا احتياطيًا واستعادة وترحيلات تشغيلية للمنصة والمتاجر. لا توجد فوترة اشتراكات أو تسجيل ذاتي أو نقل دومينات في هذه الدفعة.

## التحقق

نجحت دورة التجارة السابقة: 337 فحص HTTP. نجح 179 فحص HTTP للصلاحيات والعزل على SQLite ومثلها على PostgreSQL بقواعد مستقلة، وتشمل منتجين وعميليْن بنفس الأرقام، منع تبادل توكنات التاجر/العميل، فصل المنصة، رفض قاعدة مكررة، رفض مضيف مجهول، فصل صور الرفع، تعليق متجر واستئنافه دون التأثير في الآخر. نجحت اختبارات مخطط PostgreSQL الـ33 وبناء Angular للإنتاج وAPI.

```powershell
pwsh -File tests/security-smoke.ps1 -AdditionalChecks tests/product-order-checks.ps1
pwsh -File tests/security-smoke.ps1 -AdditionalChecks tests/tenant-isolation-checks.ps1
pwsh -File tests/postgres-schema-checks.ps1 -PostgresBin <postgres-bin-path> -ApiIsolation
```

الفحوص تستخدم قواعد مؤقتة ومنافذ محلية. يلزم اختيار `--context ShopContext` لأوامر ترحيل المتاجر بعد إضافة سياق المنصة. EF tooling له ShopDesignTimeFactory مستقل عن حل مضيف HTTP، ويدعم تمرير `--store-connection MerchantB` بعد `--` لاختيار مرجع مضبوط على الخادم. لا تشغل database update على قاعدة حية دون نسخة احتياطية ومراجعة هدف الاتصال.
