# تأمين الصور وتتبع الطلب — 26 أكتوبر 2026

## رفع الصور

رفع التاجر يقبل PNG وJPEG وWebP فقط، بامتداد ونوع محتوى مطابقين للصيغة التي يكتشفها decoder. حد الملف الأصلي 5MB وحد طلب multipart هو 6MB. ترفض الصور غير القابلة لفك البكسلات كاملة، والصور المتحركة التي يكتشفها decoder، والأبعاد فوق 8192 لكل جانب أو 16 مليون بكسل. لا يعتمد القرار على توقيع أول الملف وحده.

تفك الصورة وتصحح اتجاه EXIF ثم يعاد ترميزها إلى WebP ثابت بجودة 90، مع حد 10MB للناتج. لا ينسخ المصدر الخام أو metadata أو payload مضاف لآخر الملف إلى wwwroot. المصدر مؤقت في الذاكرة، والاسم النهائي UUID وامتداده .webp، داخل مجلد المتجر المعزول. المحتوى الشفاف يرسم فوق سطح شفاف مهيأ. معالجة الصور محدودة بعمليتين متزامنتين لكل hostname مع طابور 20، والضغط الزائد يرفض 429.

المعالجة تستخدم [SkiaSharp 3.119.4](https://www.nuget.org/packages/SkiaSharp/3.119.4) مع [NativeAssets.Linux.NoDependencies](https://www.nuget.org/packages/SkiaSharp.NativeAssets.Linux.NoDependencies/3.119.4). اختبارات هذه الدفعة أجريت على Windows؛ وجود حزمة Linux لا يعني إجراء اختبار تشغيل Linux.

روابط صور PNG/JPEG/WebP القديمة تبقى متاحة لمتجرها. صيغ الرفع الأخرى، ومنها SVG وHTML، محجوبة عند الخدمة حتى إن كانت موجودة سابقًا؛ لا تحذف الملفات القديمة تلقائيًا. Static responses تحمل X-Content-Type-Options:nosniff. اختيارات الملفات في واجهات المنتج والمتغير والتصنيف متوافقة مع الصيغ المدعومة.

## التتبع

رقم الطلب وحده لا يكشف المنتجات أو الأسعار. يقبل GET /api/ordertracking/{orderNumber} إحدى طريقتين:

1. JWT عميل موثق من نفس المتجر، والطلب يحمل CustomerId الخاص به.
2. كود سري للطلب في هيدر X-Order-Tracking-Token، وهو إذن حامل الكود لقراءة ملخص ذلك الطلب.

الكود HMAC-SHA256 مربوط بغرض guest-tracking-v1 ومعرف المتجر ورقم الطلب، مع مقارنة ثابتة الزمن. لا يقبل الكود في query string ولا يضاف إلى روابط التتبع. تدوير مفتاح JWT يغير الأكواد؛ لا توجد آلية إلغاء منفردة لكود طلب في هذه النسخة. يجب التعامل مع الكود كسر ومشاركته فقط مع من يحق له الاطلاع على الطلب.

طلب بلا إذن وطلب غير موجود يعطيان نفس 404 العام. التتبع يحمل no-store وReferrer-Policy:no-referrer، وله حد 30 محاولة في الدقيقة لكل IP/hostname، وبعده 429. خلف proxy يجب ضبط عناوين الـproxy الموثوقة صراحةً؛ التطبيق لا يثق في هيدرات IP عشوائية.

أوقفت GET /api/ordertracking/by-email: الرد 404 دون الاستعلام عن وجود البريد أو طلباته. أزيل البحث بالإيميل من الواجهة. العميل المسجل يتتبع طلبه بحسابه، والضيف يستخدم رقم الطلب والكود الخاص الظاهر في تأكيد الشراء. المتصفح يحتفظ به محليًا حسب hostname ورقم الطلب لتعبئته عند الانتقال من صفحة التأكيد، ولا يرسله في URL.

الطلبات القديمة لا تُفتح بأرقامها بعد التحديث. يستطيع التاجر، داخل لوحة طلبات متجره، اختيار Show private tracking code للحصول على الكود ومشاركته مع صاحب الطلب بعد التحقق منه. API الإدارة هو GET /api/merchant/orders/{id}/tracking-access، ومتاح للتاجر فقط مع no-store. العملاء لا يستطيعون توليد أكواد طلبات أخرى.

إعادة Checkout لمحاولة محفوظة تتحقق من هوية المحاولة والبصمة أولًا ثم تضيف trackingToken حاليًا إلى التأكيد، حتى للإيصالات السابقة التي لم تتضمنه، دون إعادة إنشاء طلب أو إرسال إيميل جديد.

## التحقق

نجح 419 فحص HTTP للتجارة والطلبات والحماية، تشمل:

- رفع صورة سليمة وعرضها وإعادة رفع WebP الناتج، مع استمرار معرض صور المنتجات والمتغيرات.
- رفض سكربت متنكر كصورة، SVG، امتداد مزدوج غير مسموح، اختلاف MIME أو decoder، ملف مبتور، ملف أكبر من الحد، وصورة عريضة فوق الحد.
- إزالة payload ملحق بصورة سليمة، وحجب SVG قديم، والتحقق من nosniff.
- رفض رقم الطلب فقط والبريد فقط وحساب عميل آخر وكود لطلب آخر وكود في URL؛ قبول صاحب الطلب أو الكود الصحيح؛ منع caching وتقييد التخمين.
- اختبارات متاجر SQLite وPostgreSQL تشمل رفض كود متجر أ في ب وقبول حساب صاحب الطلب، مع استمرار Checkout الآمن والباقات.

```powershell
pwsh -File tests/security-smoke.ps1 -AdditionalChecks tests/upload-tracking-security-checks.ps1
pwsh -File tests/postgres-schema-checks.ps1 -PostgresBin <postgres-bin-path> -ApiIsolation
```

لا تحتاج هذه الدفعة ترحيل قاعدة إضافيًا. ما زال خارجها: استعادة كلمة المرور وتأكيد البريد، تحديث الإطار والحزم القديمة، وإعدادات أسرار/HTTPS/monitoring ونسخ احتياطي إنتاجية.
